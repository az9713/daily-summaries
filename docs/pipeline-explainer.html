How the plumbing works

The daily-summaries audio pipeline

Git is superb at tracking text and hopeless at storing audio. So this system keeps the HTML summaries in GitHub where they belong, moves every podcast MP3 to Cloudflare R2, and leaves the web pages to simply point at the audio there. Below is the whole story: the problem, every component, where GitHub and Cloudflare actually meet, every credential decoded, the life of one episode, and the questions you didn’t know to ask.

The problem: Git was never built to store audio

The website is a GitHub repository of HTML pages, served for free by GitHub Pages at az9713.github.io/daily-summaries. Each day it also produces one podcast MP3 per summary — and those MP3s were being committed straight into Git alongside the HTML.

Here is the trap. Git keeps every version of every file, forever — complete history is its entire purpose. For text it does this cheaply, storing only the differences between versions. But Git cannot diff two binary files like MP3s, so each time an audio file changes it stores a whole fresh copy, permanently. Audio is already compressed, so it never shrinks further either.

That compounds daily. The repo’s hidden .git store had swollen to roughly 950 MB with no ceiling in sight. Every clone gets slower, forever, and GitHub Pages carries soft limits on size and bandwidth that this would eventually hit. You also cannot simply “delete” a file out of Git history — removing it means rewriting history.

The fix is the single idea that makes everything else make sense: keep the text (HTML) in Git, which is what Git is good at, and move the big audio files to storage built for serving files — with the web pages just pointing at them.

How the pipeline fits together

Muse only ever pushes to the repo’s main branch; everything after that is automatic. Watch the dots: the amber one is an MP3 being carried off to Cloudflare R2, the blue one is the HTML page staying inside GitHub on its way to the reader.

How GitHub actually “talks to” Cloudflare

A common misconception is that there is some partnership or direct company-to-company link between GitHub and Cloudflare. There isn’t. What actually happens is humble:

A program (rclone), running on a GitHub Actions virtual machine, makes ordinary HTTPS network calls to Cloudflare R2’s S3 endpoint, presenting the S3 credentials to prove it is allowed. GitHub-the-company and Cloudflare-the-company don’t know about each other. They are just two services, and our little script holds keys to both.

rclone uses only the Access Key ID + Secret Access Key pair (the “S3 credentials”). That token can be scoped to one bucket with read/write only, and given an expiry: we first used a 24-hour token for a one-off, then a non-expiring one for the permanent pipeline.

Why so many? Separation of concerns and least privilege. Each credential proves a different thing to a different system, and scoping plus expiry limit the damage if any one leaks. It is not redundancy — it is layered security.

Why the robot doesn’t loop forever

The janitor’s last act is to commit the rewritten HTML back to main. A push normally wakes the janitor — so why doesn’t this one start it again, and again, forever? Because GitHub deliberately does not re-trigger workflows for pushes made with the automatic GITHUB_TOKEN.

The journey of one episode

End to end, from the moment Muse files a new summary to the moment a listener hits play. (The step numbers light up in sequence.)

  1. Muse writes and pushes. A new summary’s HTML (with a ../podcasts/new.mp3 link) and the new.mp3 file are git-pushed to main.
  2. The doorbell rings. That push starts the offload-audio-to-r2 janitor in GitHub Actions.
  3. A throwaway VM boots. GitHub spins up a fresh Linux machine, checks out the repo, and installs rclone.
  4. rclone uploads the audio. Using the S3 credentials from the GitHub secrets vault, it copies new.mp3 to the R2 bucket over HTTPS.
  5. It verifies the upload. The workflow confirms the file is actually on R2 before touching anything else.
  6. It rewrites the page. ../podcasts/new.mp3 becomes https://pub-….r2.dev/new.mp3 (and it fixes the JS player’s selector so progress tracking keeps working).
  7. It removes the local copy. git rm new.mp3 — the file is safely on R2 now.
  8. It commits back. The change is pushed to GitHub using the throwaway GITHUB_TOKEN. This push does not re-trigger the janitor, so there is no loop.
  9. Pages rebuilds. GitHub Pages regenerates and serves the updated HTML.
  10. A visitor presses play. Their browser loads the HTML from Pages and streams the audio from R2’s pub-….r2.dev URL, which supports range requests so seeking works. They notice nothing different — that is success.

Things you didn’t know to ask

Will this cost money?

The R2 free tier is 10 GB of storage, zero egress (bandwidth) fees, and generous operation limits. This project (~1 GB) should cost $0. A card is on file but is not charged unless you blow past the free tier. Keep an eye on the R2 usage meter.

What if a workflow run fails (R2 down, bad token)?

The episode simply stays un-offloaded: the MP3 remains in the repo and its link stays local, so the site still works — Pages serves the file directly. The next successful push self-heals it. Failures are safe, not site-breaking.

Is the audio public to the whole world?

Yes — anyone with the URL can download it. That is fine here, because the audio is already public on the site. But do not put private files in a public bucket.

How dangerous is the non-expiring token?

It is convenient but must be guarded. If you delete or rotate it in Cloudflare, the pipeline breaks until you update the two GitHub secrets. If it ever leaks, someone could read and write only this one bucket — that is the entire blast radius, by design.

Could a malicious pull request steal the secrets?

GitHub does not pass repository secrets to workflows triggered by forked pull requests — a built-in protection. Just keep the repo’s own workflows trustworthy.

Why is the repo still big after all this?

History still holds the old audio blobs until GitHub garbage-collects them, so the billed repo size may lag. GitHub Support can force a cleanup.

Could Muse ever undo the janitor’s work?

If Muse ever force-pushes, it could clobber the janitor’s commit or resurrect old blobs. Normal (non-force) pushes are protected by Git’s fast-forward rule, so in everyday use this is safe.

Is the pub-….r2.dev URL production-grade?

No. It is a rate-limited “development” URL. If traffic grows, attach a custom domain to the bucket for a real CDN.

What else could break a run?

The workflow fetches the rclone installer from rclone.org on each run; if that is ever down, a run fails — safely, as above. It could be pinned to a fixed version later.

Do I need to understand all of Cloudflare?

No. Cloudflare is a big company (CDN, DNS, security). We use only its R2 storage product and the bucket’s public URL. You can ignore the rest.

Is there one chore left?

Yes. Because Muse commits MP3s before the janitor strips them, full Git history still creeps a few MB a day and needs an occasional manual purge — unless Muse is repointed to push to a staging branch. Then main never sees a raw MP3 and history stays flat forever. That is the one open upgrade.

Glossary

bucket
A named container inside object storage that holds files, like a top-level folder. Ours is daily-summaries-audio.
egress
Data leaving a service to the outside world (downloads). Most clouds bill for it; R2 charges zero egress fees.
range request
An HTTP request for just part of a file. It lets a browser jump to the middle of audio without downloading all of it — essential for seeking.
object storage
Storage that holds whole files (“objects”) addressed by name over HTTP, built for serving files cheaply at scale — unlike a code repository.
CI/CD
Continuous Integration / Continuous Delivery: automation that runs on each change. GitHub Actions is our CI/CD.
YAML
A plain-text format for configuration, written with indentation. Our workflows are YAML files in .github/workflows/.
S3 protocol
The de-facto standard API for object storage, created by Amazon. R2 speaks it, so standard tools like rclone work unchanged.
static site
A website made of pre-built files (HTML, CSS, JS) with no server-side app. GitHub Pages serves exactly this.
